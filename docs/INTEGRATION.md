# EVORA integration and verification runbook

**Published coordination-branch draft; not a running API or executed benchmark.** The full initial proposal is fixed scope and delivered in stages. [Proposal](PROPOSAL.md)/[traceability](PROPOSAL_TRACEABILITY.md), [catalog](TASK_BREAKDOWN.md), [DESIGN.md](../DESIGN.md) and `specs/openapi.yaml` version 0.2.0 are the shared base. No operationId is added: use the same 25 canonical operations and generated types.

## Stack and authority

React + TypeScript → FastAPI/Python API → authoritative SQLite + private original files + versioned/rebuildable Neo4j projection. Backend alone accesses databases/storage. Neo4j is graph storage/querying, not the scoring algorithm; no second Streamlit dashboard. G01/G01B/G01D establish tested package/driver/model versions and local commands, G01C tests Windows skeletons. Nothing here claims packages installed or a tested implementation baseline.

SQLite owns cases/access, evidence metadata, completed immutable processing outputs, analysis snapshots/findings/triage/history and private versioned audit/provenance. Original bytes/hash never change. SQL pending run/output precedes idempotent Neo4j `(case_id, analysis_run_id)` partition writes. Verify graph/source/finding/triage coherence before publishing SQL completed pointer. Hide partial partitions; crash/retry/rebuild tests are mandatory A01B/A05 proof. No distributed transaction/dual-write success assumption.

## Contract behavior to exercise

- All operations declare invalid input as 400 ApiError; shared FastAPI mapping must not leak default 422 validation. Missing/invalid identity is 401; missing/foreign case-scoped resource/selector is 404 without existence leak. Only use status responses declared on each operation. C-03/C-04 still choose auth and format/failure policy.
- `startProcessing`/`startAnalysis` accept idempotency keys scoped actor+case+operation. Fingerprint method/path/explicit params/body. Different evidence target with reused processing key is 409. Same key/request returns same original run, including failure, **before resnapshot**; changed current server data is not a request difference. New key starts current-input work. Poll to completed/failed; upload alone is not processing or analysis.
- `startAnalysis` stays **bodyless**. Required AnalysisInputSnapshot contains case_id, all uploaded evidence_ids at acceptance, latest completed processing_run_ids per evidence by `(finished_at UTC, id UUID)`, their observation_ids and canonical lowercase sha256. Arrays are unique lexically sorted UUIDs and may be empty. Digest is SHA256 of UTF8 compact sorted-key JSON for exactly case_id/evidence_ids/processing_run_ids/observation_ids, excluding sha256. Freeze in SQL before work. Evidence lacking observations stays in manifest but not scored under G02. Original Evidence.sha256 is separate.
- Trigger is server-derived: no previous completed run→initial; different snapshot digest→new_observations (including reprocess of same file); identical digest→manual, even if algorithm version changed. Old runs/snapshots/results and source locators remain immutable.
- Latest completed analysis is ordered by `(created_at UTC, id UUID)`, not worker completion order. `getGraph`, `listFindings`, `listTriage` accept optional analysis_run_id; specified same-case completed run is pinned; missing/foreign/pending/failed→404. Omit selects latest completed. Graph/finding/triage responses must return the selected run ID even when empty. Before any completed run, empty graph/findings and unscored triage entries may omit it. UI takes completed ID from poll (or first coherent completed response), passes it to **all related reads and every page**, validates returned IDs and rejects/refetches mismatches. No mixed-run display during concurrent new analysis. Explicit switch to new run refreshes all views together.
- `listObservations` defaults to latest completed output per evidence; optional processing_run_id pins same-case completed historical output. Pending/failed/foreign outputs cannot be consumed as completed.
- GraphNode IDs are source Evidence/Entity/Event UUIDs within case, not anonymous nodes; no graph-node observation_ids requirement. GraphEdge/Finding observation_ids are nonempty unique same-case source links. Follow observations to row/page/frame/region locators and originals. Optional Finding.entity_ids supports cluster membership; missing_information supports hypothesis gaps.
- Not-scored is distinct from a computed P4. A04 uses initially available factors under G02; A17 explicitly adds all remaining factor/detector stages. Proposed weights/bands are experimental, not standards; G02 must define numeric functions/missing/ties/goldens first. No source quality inferred solely from source_label, identity from co-mention or guilt from anomaly.
- Completed `listTriage` membership is exactly selected AnalysisRun.input_snapshot.evidence_ids, total its count, including unscored manifest items; latest_result, if present, is from that run. Sort pinned computed score descending then evidence UUID ascending, unscored last by UUID, before limit/offset slicing. Uploads or new runs cannot change pinned membership/total/order. Only before first completion, unselected triage lists live unscored uploads with live total in UUID order. G02 score-level ties/bands remain policy choices, not permission to change this pagination order.
- Each triage read overlays the live latest authorized same-case override by (created_at UTC,id UUID), not an automated-snapshot override. effective_priority uses the override, otherwise the selected computed priority, and is absent if neither exists. Override changes never reorder the pinned list or change total/membership; UI must not sort by effective priority. getTriageHistory is immutable append-only automated results, not overlay history.
- supported=true answers require citations and each factual claim must be grounded; supported=false has no factual unsupported assertion and zero citations. Optional model_version/prompt_template_version/provenance_id support full generation. Store rich private inputs/outputs/model/parser/parameters/time/prompt/retrieved IDs+locators/verification internally, not raw application logs or public audit fields.

## Stage 2: genuine feedback on existing evidence

A17 assembles relationship, corroboration, source quality, temporal, conflict, gap, cluster, anomaly and hypothesis stages with G02 factors. A10B/A11B calculate actual conflict/gap relevance; A13B maps anomalies into a reviewed existing factor without adding an enum or double counting. A19 verifies discovered findings affect priorities of already uploaded evidence rather than only appearing in panels.

**I07 bounded feedback tracer:** labeled positive/negative inputs run real detector/factor pipeline. At least one meaningful existing-item factor and rank/priority change is source-backed; false-positive controls do not manufacture priority. U12A/B/D and U06B display uncertainty and old/new explanations/history.

**I07B deeper-processing tracer:** P15 internal backend policy uses discovered gap/conflict/anomaly signals to optionally choose approved deeper/reconfigured processing for the same Evidence, under a **new processing key**, not invented UI parameters/request body. U05C/U05D exercise existing operations; P15 selectors stay internal. Preserve original Evidence/hash and old outputs. A18 new-key analysis selects latest completed output by `(finished_at UTC,id)`, freezes new digest and derives new_observations. Show justified earlier rank change with new observation locators. Same-key replay retains original run; failed deeper run leaves prior completed selection usable. Input/output/algorithm provenance and old resources remain readable. Policy selection must be explicitly tested, not a mocked claim that uploading another file proves feedback.

## Stage 3: full modalities, dashboard and final LLM RAG

- P07/P08/P09/P10/P11/P12/P13/P13B and P05C/P14D exercise document/text, OCR, images, CCTV/video, mobile and transaction adapters alongside first network/GPS/messages. Document accepted layouts/encodings/models/limits and resource/uncertainty controls; retain raw/source values and all locator types. P08/P09/P10 require approved adapter/model/version and private data-boundary decisions, not G03's final generative provider choice. No physical acquisition or real banking claim.
- Dashboard includes U13 all-page evidence counts/types/status, U13B confidence/quality/corroboration/contradiction inspector, U13C entity/event inspector, U12A–E conflict/gap/cluster/anomaly/hypothesis views, source downloads, explanations/history, command/status UI and audited review/overrides. APIs only; no invented count/summary/provenance endpoint. Multi-page counts and same-run page consistency are acceptance, not optional polish.
- Full RAG is A16B retrieval over graph/entities/events/triage/findings/observations/metadata → U10B approved LLM generation → U10C claim citation verification/unsupported fallback/private provenance → U11B final UI. Deterministic U10 requires approved authorized local retrieval/grounding/privacy behavior, not the final provider choice; it alone is insufficient. G03/C-06 remains a gate for U10B/U10C full generation/verification. Test provider unavailability, injection, weak support, invalid locators, foreign-case retrieval and unsupported questions. No-paid-service CI uses explicit test adapters; full gate separately exercises actual approved provider/model with permitted synthetic data and reports its version.
- F08D/F08E verify processing and Q&A provenance regression. Rich versioned records are private authorized data; audit events expose safe references only. Hash/audit traceability is not certified chain of custody.

## Contract and PR checks

Run lint/bundle, generated types and TypeScript compilation, `scripts/verify_coordination.py <bundled-openapi-json-path>`, `scripts/test_verify_coordination.py`/`scripts/test_contract_examples.py` negative/schema-example checks and DESIGN lint on this branch and PRs. Exact actual artifact outcomes belong to `PREIMPLEMENTATION_REVIEW.md`; this runbook defines future app execution, not results.

Use one bounded task/common spec commit/allowed path set per fresh branch/session. Four people each own one module; one synchronizes shared files alongside their module. Schema-derived independent tests are allowed before upstream merge; integration requires real producers. Needed C-03–C-06 gates, assignees and tested setup stay explicit; review/setup/unaffected work proceed. No autonomous `main` edit or authorized-scope expansion.
