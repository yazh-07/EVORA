# EVORA integration contract and synthetic case

**Status: local coordination draft, not a working API.** The selected stack and three-CSV **first integration tracer** are described below; the full proposed initial feature scope remains the build goal. Four people each work on one module; one of the four coordinates integration alongside their module. Affected modules settle HTTP/auth details as their tickets need them, and agents use one published contract commit. Proposed paths, request/response fields and enums are in `specs/openapi.yaml`; do not make up alternate routes or treat unpublished local files as a shared base.

## Implementation baseline

- Python/FastAPI backend, SQLite metadata for a single-machine prototype, private local artifact directory, TypeScript/React client. A modular monolith avoids coordinating four services. No mandatory Neo4j, external vector DB or remote LLM for the initial tracer. Resolve operational details with the affected modules and verify them with code/tests rather than adding formal titles.
- The spec provides a variable localhost development server; clients configure their actual base URL. `specs/openapi.yaml` alone owns HTTP names and wire models; do not maintain hand-written competing schemas or copy the same model into a second file as another authority. Generate typed clients/models from the accepted spec where practical.
- IDs are opaque UUIDs; timestamps are RFC 3339 with UTC offset for normalized values. Preserve the source timestamp string, including ambiguous/no-zone strings. Hash original bytes with lowercase hex SHA-256. `source_label` is metadata, not proof of independent provenance. Case scoping is enforced by backend authorization, not merely a filtered frontend query.
- The schema enumerates evidence **categories**, not a claim that all file encodings within them work. Upload may preserve a file that has no processor; processing returns 415 or an explicit failed run. The three documented CSV formats are the first integration tracer; document text, OCR, images and video remain on the wider roadmap as separate tested format/model tasks.
- Processing and analysis POSTs return run records. Poll the corresponding GET until `completed` or `failed`. No caller should query mutable partial observations/findings as completed outputs. Read views show latest *completed* analysis. Repeated submissions with the same Idempotency-Key and same inputs return the same run (202); same key and different inputs return 409. A new analysis run uses a new key.
- The first analysis run can score the available observations/graph; a later run after new observations is re-triage. `TriageResult` is append-only; manual override is a separate audited object and never rewrites the computed score. Before any completed analysis run, `GET /triage` returns an entry for each evidence item with neither `latest_result` nor `effective_priority`; the UI shows **not scored**, not a fabricated P4. No fabricated factors.
- Baseline priority bands proposed in the source document: P1 80–100, P2 60–<80, P3 40–<60, P4 <40. Candidate factor weights from the document are relevance .25, connectivity .20, corroboration .15, gap_relevance .15, source_quality .10, conflict_relevance .10, temporal_proximity .05. These are **prototype choices, not forensic standards**; M3 owns precise factor functions, missing-data treatment and versioning and must publish a tested algorithm policy before scoring code is merged. Agents must not independently fill in missing factor semantics. Sum contributions to the reported score; show factors, evidence IDs, trigger and run/version for every score.
- Bearer auth is part of the proposed API; identity provider, roles and local developer fixture tokens still require a team decision. Never hard-code a shared production token. Unauthorized and foreign-case IDs must not leak evidence metadata or existence; return 404 for foreign-case resources. Frontend should not cache original bytes persistently or log tokens.
- The full proposed initial scope includes alternative hypotheses, clusters, anomalies, conflicts, gaps, grounded Q&A and visual/video analysis. Their **interface slots** are in the spec, but none of these is implemented. Plan separate reviewable increments; keep unsupported operations honest, and agree an explicit error response in the spec before exposing them; never fabricate success payloads. Staging work is not cutting the agreed overall feature goal.

## Synthetic end-to-end tracer (only synthetic data)

Files in `fixtures/synthetic-case/` are test input, not evidence from a real person. On Windows use the same repository-relative paths. CSV encodings are UTF-8, comma-delimited with the header row shown. The first-tracer file formats are `network.csv` (`network_log`), `gps.csv` (`gps`), `messages.csv` (`message`). Parser-specific conventions must be documented before adding other files.

1. Create case A; upload `network.csv` and `gps.csv` to case A. Check that both downloads equal input bytes and hashes match. Upload the same file into case B and check all cross-case reads, jobs and review actions are inaccessible.
2. Start processing for A's first two files. Poll run resources; verify observations retain original row locator, raw values, normalized values, original/normalized timestamps, `processing_run_id` linking to the run's parser version, and corresponding Evidence IDs. Network contains device `D-7`; GPS contains `D-8`. Neither is a verified person's identity and the first two files do **not** themselves establish a cross-file device match.
3. Start an initial analysis run; record graph, findings and triage history. Graph edges and findings have supporting Evidence IDs. Do not require a predetermined numeric score from the not-yet-finalized scoring algorithm.
4. Upload/process `messages.csv` (a synthetic text row mentioning both `D-7` and `D-8`), run analysis again with trigger `new_observations`. Check that new source-backed observations make a *candidate* connection between previously disconnected items and that relevant factor/explanation inputs change. The tested scoring policy must produce an explainable **priority/rank change** for at least one earlier item; if it does not, adjust the synthetic fixture and policy together *before* claiming adaptive triage. Old runs and old `TriageResult`s remain intact. Co-mention is not proof the devices or their operators are associated.
5. Review one supported finding and override one evidence priority. The review and override show the authenticated actor, time and reason in audit events. Automated score history remains untouched; effective priority reflects the override.
6. Ask which evidence suggests a connection between `D-7` and `D-8`; a cautiously worded answer gives claim-level citations to A's relevant Evidence IDs **and source locators**. Ask an unsupported identity question and require `supported=false`, no factual identity claim, and an empty citations array. Every citation target must exist in the authorized case and support the stated claim.

## Test gates before PR merge

- Contract lint and generated client/type check against the accepted OpenAPI spec.
- Backend API/format fixtures, hash + byte equality, invalid file/size handling, run lifecycle and duplicate-key tests.
- Cross-case access negative tests for *every* read/write path; auth failures, invalid UUIDs, foreign IDs and non-existent IDs.
- Scoring invariants: 0–100, factor sums/reasons, deterministic given algorithm version, append-only history, changed/new observation run, manual override separate from automated score.
- UI happy path + disabled/empty/error states; never silently display placeholders as computed facts.
- No live external model/paid service in CI; use deterministic synthetic inputs. If later using remote inference, obtain explicit team privacy decision first.

## PR/handoff protocol

Work on a fresh **one-ticket** branch from the common base, selecting an ID from `docs/TASK_BREAKDOWN.md` rather than an entire module/milestone. Give each agent an assigned module/person, input/output contract, allowed paths, exact acceptance tests and shared schema commit. A change to `specs/openapi.yaml` is coordinated with affected producer/consumer modules; update fixtures, generated types, API tests and callers in the same PR or a coordinated migration. The person coordinating integration updates the roadmap to avoid simultaneous edits. Commit/push/merge authorization follows `AGENTS.md` and user instructions. `main` is the stable base; add `develop` only if a staging branch is useful.
